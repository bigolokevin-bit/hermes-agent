# Design: 层级从路由解析来，不从文案猜

## 层级的事实源

顶栏不自己维护「哪页该显示什么路径」的第二套台账，而是复用路由表已有的解析结果：
路由命中记录本身就带模块、是否详情页、员工编号与分区。面包屑 = 把命中结果拼成
「分组 › 模块 › 员工详情」，每段的可点目标 = 该层级对应的真实地址。

推论：凡是路由表新增/改名的页面，面包屑自动跟上；路由解析不到的页面（插件路由）
退回共享解析器，宁可显示派生标题，也不显示假的「控制台」字样。

## 返回钮的边界

返回钮是「有上一层才出现」：层级 ≥2（即详情类页面）才渲染，点击回到上一个历史条目。
模块列表页没有上一层，加箭头只会让层级更糊。用户原话是「不知道怎么返回」，
所以不能只靠可点面包屑——必须有一个看得见、位置固定的钮。

## 查询串分区为何要单独读

分区有两种形制：路径段（`/employees/:id/config`）与查询串（`?zone=config`）。
路径匹配会先命中工作台那行，分区字段恒为默认值——只读命中结果的分区字段，
查询串形制就永远显示「工作台」。设计要求：**两种形制解析出的分区必须相同**，
别名字符串（如 `audit`→证据分区）同样归一。这是 29 条路由里唯一一处不一致，
已用契约测试钉住（顶栏源码必须同时覆盖两种形制）。

## 已知边界

- 面包屑最后一段（当前页自身）不可点——点了也是原地，链自己会误导「还能下钻」。
- 裸工作台页不出现「员工详情」自链段；返回靠箭头钮。
- 分区词表两处维护（顶栏 / 页内分区条），一致性靠词表同源约定与验收场景保证。
