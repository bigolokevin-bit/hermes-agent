# Proposal: 每个数字员工自己的「人格」（SOUL + 叠加层）

## 背景

控制台里每开一位员工的对话，实际跑在 Hermes 的一个 profile 上。此前所有员工共用
默认档，于是「对话里的自称」与「名册里的这个人」没有必然关系；改为每员工独立档后，
克隆默认档又会把**上一位员工**的 `agent.system_prompt` 一起复制过来（实测：新建档里
写着 `employee_id=emp_9F42AAE2…` 的「AgentOS 产品助理」），模型会同时看到两个人。

用户决定（原话）：

- 「每个 Agent 都要支持独立的 soul，因为他们在企业级的办公场景下，各自有各自的任务和角色职责定位」
- 「我需要建档的时候，在 WebUI 这边新建数字员工的时候就要去配置。如果管理员用户懒得填的话，就有一段默认的soul。」
- 「如果把它的默认的删了，我担心会影响到 runtime，所以数字员工单独的 soul.md 可不可以叠加在它上面？」

因此本 change 的边界是：**身份写 SOUL.md；Hermes 的通用叠加层不删，只把内容换成这位员工自己的组织上下文。**

## 变更内容

1. 新建员工表单增加「人格 SOUL（可选）」：留空按姓名/岗位/部门/岗位职责自动生成；填写则原样写入。
2. 员工第一次打开对话时，确保其独立档 `emp-<8位>` 存在；建档请求同拍带上 `soul=`。
3. 控制台建的档（描述含「控制台自动创建」）在每次打开时把 `SOUL.md` 与
   `agent.system_prompt` 对齐到当前员工档案：身份变了改 SOUL，组织上下文变了改叠加层。
4. 用户自己写的人格（无受管标记且非控制台建档）**永不覆盖**。
5. 素材不全（缺姓名/岗位/含职责的版本）时不建档，退回默认档并说明原因——不拿别人的开场白顶上。
6. 叠加层写回失败不影响对话，但必须在界面上说明。

## 不改什么

- 不删除 `agent.system_prompt` 这一层（Hermes 的补充说明能力）；
- 不改 Hermes 的行为约束与工具指导（与身份槽无关）；
- 不改域侧员工/版本契约，不改 BFF 路由；
- 不做每员工独立通信渠道（另开 change）。

## 依赖与风险

- 依赖读口：`GET /api/employees/<id>`、`GET /api/employee-versions?id=`；
- 写口：`POST /api/profiles`（含 `soul`）、`PUT /api/profiles/<name>/soul`、
  `PUT /api/config?profile=<name>`（深合并写 `agent.system_prompt`）；
- 风险：网关会缓存配置，改完叠加层后已有会话可能仍用旧值 → 需要新会话或重启才生效；
- 风险：`SOUL.md` 与叠加层若两处都写身份，会出现「两个我」，所以叠加层必须显式让位。
