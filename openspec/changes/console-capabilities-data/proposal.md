# Proposal: 能力与接入页对接真读口（工具/模型/价目/MCP/提案）

## 背景

能力与接入页此前多处「指到了不存在的上游」：工具清单读的口在上游是 404、
模型目录同样（上游根本没有那个路由），结果「有数据的上游」被显示成「空集」，
与「真 0」无法区分——这类假空态直接污染治理判断。同期取证确认：
工具组清单与模型目录都有真读口；价目随模型目录同包下发；MCP 服务器当前确实是 0；
技能提案服务已在 8104 起来（`/v1/skill-proposals`），但 BFF 的
`/api/skill-proposals` 还没指过去。

本 change 把「能力与接入页只讲真话」定为规格：每块数据必须来自真实存在的读口，
空与失败必须分陈，供应商/模型/价目按上游真形制摊平上屏。

## 变更内容

1. 工具清单改从工具组真读口取数，不再经过失效的探测路由。
2. 模型目录改读真端点，按「供应商 × 模型」摊平上屏（当前真形制：5 供应商、148 模型）；
   上游进程状态异常（如需重启）时如实报错，不假装目录为空。
3. 价目与模型目录同源读取并上屏；上游没有随包价目时呈现「未接线」，不编价目行。
4. MCP 空清单的表述明确区分「真 0」与「加载失败」。
5. 提案队列块声明其数据源必须是提案台账；台账未接通前按缺读口呈现。

## 不改什么

- 不改页面骨架与分卡布局；
- 不新增「可发现技能」等无上游的块（继续按缺读口声明）；
- 不在本 change 内完成提案链路接通（BFF 指向、launchd 常驻、提案页接线单列任务）；
- 不把实测读数（148/5 等）写成规格需求——它们属于 evidence，规格只钉「摊平可数、
  来源真实、空败分陈」的行为。

## 依赖与风险

- 证据提交：`0ef7c3de03`（工具清单）、`4ebcf08c44`（模型目录端点）、
  `550611de60`（providers 摊平 + 随包价目）、`98ae4863b9`（真 0 与缺读口分声明的口径）；
- 提案服务：`/v1/skill-proposals` 已在 8104 起（临时进程，未转 launchd）；
- 风险：真读口上游有「进程代码落后于检出即拒绝服务」的保护，页面必须把这类
  503 原样呈现为故障，而不是换一条能返回空的路由兜底——换路由兜空集正是本 change 修掉的病。
