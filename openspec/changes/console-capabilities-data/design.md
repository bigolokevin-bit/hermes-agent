# Design: 读口必须真实，空与失败必须分陈

## 三条口径

1. **每块数据指名道姓一个真读口**。此前「上游 404 的路由 + 空态回落」的组合，
   把「读不到」渲染成了「没有」——治理页最不能犯的就是这个。改法不是加兜底，
   而是把口指到真实存在的路由上：工具 → 工具组清单口，模型 → 模型目录口
   （`/api/model/options` 这一形制），价目 → 与模型目录同包（无独立端点，
   按独立端点读永远空）。
2. **上游真形制决定摊平方式**。模型目录回包是「供应商数组，各带模型与价目」，
   页面就按供应商摊平行，行数 = Σ各供应商模型数；不是行数组就判缺失，
   不退回「按通用键猜」——猜错同样是静默空表。
3. **真 0 要说破**。MCP 当前确实 0 个服务器：界面写「清单是空的（真零，不是加载失败）」；
   上游故障/缺读口/确认空集三态各用各的措辞，不得共用「暂无数据」。

## 状态码的忠实呈现

模型目录口在「进程代码落后于检出」时返回 503 restart required。页面把该故障
原样上屏（可重试），**不**换一条会返回空的路由兜底。曾经的事故正是探测腿失效
把有数据显示成空集；兜底换口等于复发。

## 提案链的现状与目标形制

- 提案服务 `/v1/skill-proposals` 已在 8104 起来，但是临时进程，重启即消失；
- BFF 的 `/api/skill-proposals` 路由尚未指向它；
- 控制台提案页此刻按「缺读口」呈现——这是**正确的现状**，不是待修的 bug；
  待修的是上游链路（见 tasks 3）。
- 接通后的验收口径不变：提案队列行可数、按影响面排序、空集写「真零」。

## 已知边界

- 「可发现技能」「提案差异」「准入线」三块没有上游，继续整列不画 + 缺读口声明
  （`98ae4863b9` 口径），接通才上屏；
- 供应商/模型/价目的具体数量（5/148）是当日实测读数，归 evidence；
  规格只钉「摊平可数、同源价目、空败分陈」。
